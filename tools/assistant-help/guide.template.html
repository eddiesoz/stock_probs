01

Start where you are

Open, resize, and return to your work

Use the named assistant launcher when you want help. On desktop, the panel stays alongside the workspace; use its expand, minimize, history, and close controls as needed. On a narrow screen it becomes a full-screen surface with safe-area spacing. The message area normally scrolls independently, and the composer stays available as the on-screen keyboard opens. While an exact WebFetch URL approval is open, scroll the panel itself to keep the full destination and its decision together.

The launcher appears after the app checks your sign-in and assistant status. Opening it checks your sign-in again, then loads the model catalog and recent conversation history and requests the current page context; it does not send a prompt, start a model turn, or run public search. Selecting New conversation creates and saves a separate conversation but sends no assistant request until you send a prompt. Choose a model, write a question, and send it when you are ready. Closing the panel returns you to the page.

On a phone, close the assistant to return to the same workspace, then use the assistant launcher to reopen it. The launcher regains focus so you can continue with the keyboard.

Research only. The assistant does not place trades or orders. Its answer can be wrong, so verify important figures against their cited records.
02

Know what is enabled

Choose a model that has been reviewed

When you first open the assistant, no model is selected. Choose an approved usable model before sending, then review the exact provider terms and displayed privacy/data-use, training, confidential-data, and billing statements. Console catalog-review statements are administrator-supplied and unverified. Models whose terms permit prompt or context collection require a separate, version-specific opt-in; models excluded by policy remain unavailable even with consent. The assistant does not silently switch providers or models, use a paid fallback, or top up an account.

For an administrator

Administrators manage connections, credentials, and model policy in protected Provider settings after a fresh authenticator check. Keep credentials and authorization codes, including authenticator or recovery codes, out of chat. OpenCode Console is optional; its credential is used only to discover that account’s model catalog and is separate from the provider credential used for model requests. Catalog discovery is not a user sign-up step; do not create a new Console account to follow this guide. Administrator review does not replace a user’s required data-collection opt-in.

For a researcher

Select one of the approved usable models. The assistant does not silently switch to a paid model, top up a balance, or retry through a different provider.

Your selected provider may receive your message, the page context you chose to share, and tool results needed for the answer; these can include private workspace information. Check the context preview and selected model’s disclosure before sending. Conversation content and compact tool receipts are stored in owner-scoped Signal Ledger application storage, subject to storage limits. Deleting a conversation clears its active content and cache while retaining a compact, non-content audit record. Previously created backups may retain copies under the configured backup-retention policy. Provider credentials and endpoint controls appear only where the reviewed provider capability supports them. Do not put passwords, API keys, authenticator or recovery codes, or invitation codes in a prompt.

03

Share only what helps

Preview page context before you send

The panel has one sharing control for all available workspace references: turn it on to include the full set, or off to omit references. You cannot deselect individual references, and the current page route is always included either way. Open Preview to inspect the route and reference set; after changing page context, select Refresh preview before sending.

  • When sharing is on, inspect the exact route and all available instrument, event, and saved-result references before sending.
  • With sharing off, requests still include the route only; instrument, event, and saved-result references are omitted.
  • If the workspace page context changes, select Refresh preview so it reflects the current route and available references.
  • The preview explains what is available. It does not grant access to another user’s data or hidden account details.

A request may send your message, the page context you approved, and the tool results needed to answer to the selected provider. The preview describes selected workspace references; it is not a promise that all retrieved tool results are public. Review the model’s terms and avoid sharing details that are not needed.

Read the answer and its sources together

Conversation answers are saved with their timestamps and the available context snapshot. Tool activity identifies retrieved workspace evidence; the assistant’s explanation remains a separate layer. Source cards show the title and retrieval time the application actually has.

05

A suggestion is not an action

Review the exact preview before confirming

When the assistant proposes a supported workspace change, it displays a card with the action, the affected item, and the expected change. Check the details. To proceed, type the exact confirmation phrase shown on that action card and select its confirmation button. This phrase is for workspace action cards, not WebFetch. If a preview has expired, its saved page context is stale, or it belongs to another sign-in session, ask again for a fresh preview; it cannot be confirmed from history.

History-filter handoffs are available only on the Signal Ledger home (/) and open its Search ledger form, separate from Overview. From any supported page, you can ask for a filtered CSV or JSON export; after confirmation it opens an owner-authorized download. The separate Research page shows five recent records from the newest 100 and saved-forecast comparisons. The assistant can search owner-scoped history there, but to apply filters use the home page’s Search ledger form.

On Markets, confirmed requests can apply local quote filters, change the chart range or visible columns, and refresh quotes, the watchlist, or the selected chart. Review the proposed settings before confirming. These actions use the current page’s controls and selected instrument; quotes remain provider-labelled research data, not a real-time or trading feed.

On Live Trading, a confirmed request to open note controls or remove an alert is a handoff. On mobile, the assistant closes and focuses the Notes or Alerts section heading. Finish the change in that workspace control; the handoff itself does not edit the note or remove the alert. Reopen the assistant’s conversation history and select the same conversation to review its receipt. Adding a threshold is a separate confirmed action limited to the open Live Trading page session; it has no scheduler or notification delivery.

Portfolio and watchlist. Ask to add or remove an instrument, or change a holding quantity; confirm the exact symbol and amount.

Forecasts and follow-up. A confirmed new forecast request saves a new forecast. Reopening opens its immutable saved record without calling the model again. Recording an outcome appends an observation; a fresh historical reconstruction saves a separate analysis at the chosen cutoff without rewriting the submitted forecast.

Administrator invitations. An invitation proposal hands off to protected invitation settings; it does not create or send an invitation in chat. Confirming that handoff requires recent administrator TOTP verification, and the secure form checks it again when you create or send. Email-only invitations can be redeemed only by a GitHub account with a verified email matching the invitation address. Providing a positive GitHub account ID restricts redemption to that account; the email is only a delivery destination, and a username is an optional display hint. Review the recipient details there; never paste invitation codes in chat.

A theme change affects only the Light, Dark, or System appearance setting. Account and session tasks hand off to secure Account controls. Provider settings, verified backup creation, and promoted restore stay in protected administrator forms and require fresh authenticator verification. A promoted restore revokes sessions, so sign in again afterward; confirming a handoff does not complete the secure form.

06

External search stays explicit

Review the exact query and WebFetch URL

Native WebSearch first shows the exact public search query. Review that text and approve it only if you are comfortable sending it to the search provider.

Native WebFetch is a separate step. Before a page is fetched, the assistant pauses and shows an approval card with the complete HTTPS URL and why it wants to read that page. The complete URL, including every query parameter, is sent to the destination website; the fetched page is returned to the assistant for this turn. Check the hostname, path, and query string character by character because a query can contain private account or workspace details.

  1. Open the approval card and inspect the exact URL and page purpose.
  2. Select Approve exact URL once only if you accept sending that exact public URL to its destination and returning the fetched page to the assistant.
  3. Otherwise select Decline request. WebFetch uses these buttons; it does not ask for a confirmation phrase. A redirect or later destination requires a new request and exact approval.

The approval is tied to your current signed-in session, conversation, and running turn. An expired, cancelled, or interrupted turn cannot reuse it. WebFetch accepts public HTTPS destinations; it does not make a search-text link verified or guarantee that a page is trustworthy.

Before approvingRemove names, account details, private notes, identifiers, or anything else that should not leave your workspace.

Search results are retrieval leads, not endorsements. Review each destination and its date; search-text links carry the unverified label described above.

07

Return to saved work

Reopen, rename, or delete a conversation

Conversation history keeps saved answers, context snapshots, activity, and receipts within the authenticated workspace. Reopening a saved answer reads the saved record; it does not call a model to recreate the answer.

  • Rename a conversation to make its subject clear in the history list.
  • Review old context and tool receipts with the saved answer.
  • Deletion requires its own confirmation. It completes only after the private cache is cleared. If cache purging fails, the conversation remains in history and the interface offers a retry.
  • An empty history is shown as empty; a loading or storage error is shown with its own status so you can retry without mistaking it for missing data.

Illustration: selecting a saved conversation restores its saved answer and context. The panel stays bound to the signed-in owner.

08

Keep a clear recovery path

Cancel, reconnect, and handle limits

Cancel a running turn

Use the “Stop response” control when you want to stop. The transcript remains available; a cancelled or interrupted result is not presented as a completed answer.

Reconnect after a break

If the connection drops, use the visible reconnect or retry state. Check the saved conversation before starting a new question.

Provider unavailable

Read the status and retry when appropriate. The assistant does not silently switch providers or move to a paid model.

Storage quota reached

Existing workspace data stays available. Review your conversations and delete only records you intend to remove, then retry after cleanup completes.

Cancellation or other error

A cancelled turn stays marked as incomplete. For an error, read the message and retry only after checking whether the question already has a saved result.

No background research. The assistant runs in response to an explicit request. It does not start autonomous jobs while the panel is closed.
